# volc-live-firstframe

**直播间首帧 18.5 秒 → 0.35 秒：把「改 hls_time 没用」这件事用 ffprobe 打脸，再一步步压下来。**

一个零第三方依赖的 Java 工程，把火山引擎视频直播 Live 的拉流链路在本地复现出来：
源站切片 → 边缘节点（鉴权 / 缓存 / 预热 / 出口限速）→ Java 播放器模拟起播 → ffmpeg 真实解码首帧。

所有分片都是 ffmpeg 现切的，所有首帧都是从 HTTP 拉下来再解码出来的，**没有一个是写死的常量**。

## 一条命令看结论

```bash
./scripts/prepare.sh      # 生成 40s 推流源 + 六种切片参数（约 90 秒）
./scripts/start.sh        # 源站 :9090 + 边缘 :8080，出口限速 4 Mbps
./bench/bench.sh          # 全场景实测，约 70 秒，结果写入 logs/bench-result.txt
./scripts/stop.sh
```

实测（Apple M1 Pro / JDK 19.0.2 / ffmpeg 9.0.2 / 边缘出口 4 Mbps）：

| 场景 | 分片时长 | 起播缓冲 | 首帧 | 下载字节 |
| --- | --- | --- | --- | --- |
| S0 基线 `hls_time=6` + `-c copy` | **10.0s** | 3 片 | **18541ms** | 8.30MB |
| S1 只把 `hls_time` 改成 2，仍然 `-c copy` | **10.0s** | 3 片 | **18580ms** | 8.30MB |
| S2 重新编码 + 强制 IDR 对齐 | 2.0s | 3 片 | 3721ms | 1.66MB |
| S3 起播缓冲 3 片 → 1 片 | 2.0s | 1 片 | 1373ms | 578KB |
| S4 0.5s 小分片 + 单片起播 | 0.56s | 1 片 | **354ms** | 124KB |

S1 和 S0 的分片时长、字节数、首帧几乎一模一样——因为 **`-c copy` 时切片只能在关键帧处断开，
你写 6 还是写 2，最后都由推流端的 GOP 说了算**。这是本文最贵的一课。

起播缓冲片数对首帧的影响（2s 分片，同一台机器）：

| 起播缓冲 | 1 片 | 2 片 | 3 片 |
| --- | --- | --- | --- |
| 首帧 | 1373ms | 2506ms | 3721ms |
| 下载字节 | 578KB | 1.10MB | 1.66MB |

转码阶梯（同样 2s 分片、单片起播，只换清晰度）：

| 档位 | 分片大小 | 首帧 |
| --- | --- | --- |
| 720p / 2000kbps | 516KB | 1380ms |
| 480p / 800kbps | 229KB | 631ms |
| 360p / 400kbps | 134KB | 390ms |

100 人同时进直播间（0.5s 分片、缓存清空）：

| 场景 | 成功率 | P50 | P99 | 同片回源 |
| --- | --- | --- | --- | --- |
| 不预热 | 100/100 | 1316ms | 1558ms | **27 次** |
| 预热后 | 100/100 | 1324ms | 1560ms | **0 次** |

首帧没变，但回源放大 27 倍——这才是预热真正的价值。

## 首帧到底花在哪

```
t0  请求 playlist ────────────── 48ms
    ├─ 4G 网络 RTT + 边缘鉴权 + 读缓存
t1  下载「起播缓冲」所需分片 ──── 1277ms   ← 首帧的大头
    ├─ 1 片 × 578KB ÷ 500KB/s = 1156ms
t2  解码第一个分片的首帧 ──────── 46ms
    └─ ffmpeg 解出第一个 I 帧
t3  首帧完成 = 1373ms
```

`首帧 ≈ playlist RTT + (起播分片字节 ÷ 带宽) + 解码耗时`

带宽是观众的，改不了；解码是终端硬解，几十毫秒；**能改的只有「起播分片字节」**，
而它 = 分片时长 × 码率 × 起播片数。三个乘数，正好对应下面三刀。

## 工程结构

```
live/HlsLibrary.java    解析 m3u8、按滑动窗口裁剪子 playlist（尾部未封口的残片不上线）
live/OriginServer.java  源站 :9090，切片存储（不限速）
live/EdgeServer.java    边缘 :8080，鉴权 + 缓存 + 预热 + 出口限速 + /metrics
live/LiveAuth.java      sign = md5(path.expire.key)，校验过期与篡改
player/PlayerSim.java   播放器起播模拟，分段计时（playlist / download / decode）
bench/Bench.java        ffmpeg 封装：推流源、切片、ffprobe 对账
```

接口：

```bash
# 拉流（必须带 expire + sign，否则 403）
GET /live/demo/stream/{720p|480p|360p}/index.m3u8?expire=...&sign=...
GET /live/demo/stream/{quality}/seg001.ts?expire=...&sign=...

# 运维
GET  /admin/prewarm?quality=720p&count=3     # 预热最近 N 个分片
GET  /admin/reload                           # 换切片参数后重载 + 清缓存
GET  /metrics                                # 命中率 / 回源字节 / 鉴权失败
```

## 复现要点

- 播放器**不做**内部方法调用，全部走真实 HTTP；首帧解码用 `ffmpeg -frames:v 1`，耗时也是真的。
- 边缘按连接限速 4 Mbps，等价于「每个观众各自的 4G 带宽」，避免本地无限带宽把结论抹平。
- 每次测量前 `/admin/reload` 清缓存，保证都是冷启动。
- 分片时长一律用 `ffprobe` 对账，不信控制台填的数字。

## 什么时候别用 0.5s 分片

0.5s 分片把首帧压到 354ms，代价是分片请求数变成 2s 分片的 4 倍、10s 分片的 20 倍
（每个观众每分钟：10s→6 次，2s→30 次，0.5s→120 次）。1000 人在线就是每分钟 12 万次请求。
分片变小还会让单分片的 I 帧占比升高，同码率下画质略降。

经验值：娱乐直播/带货 1~2s，赛事/强互动 0.5~1s，安防/监控可以更激进，点播回看别动。
